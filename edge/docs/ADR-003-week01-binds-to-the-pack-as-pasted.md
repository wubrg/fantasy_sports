# ADR-003: The 2026 week-1 forecast binds to the pack as pasted, not the pack on disk

**Status:** Superseded 2026-09-06 by regenerating the pack in-repo — see *Resolution* below
**Date:** 2026-09-06
**Deciders:** wubrg
**Scope:** one forecast run (2026 week 1). Not a standing policy.

---

## Context

The pack pasted to the forecaster carries `pack_sha256 = 42bca9d8…a985347` and base rates
`pass_heavy 0.2648`, `efficient_offense 0.3721`. The pack committed at
`edge/beliefs/2026/week01.input.json` carries `e4465d9e…ca14c61a1` and `0.3353` / `0.3243`.

Everything else is identical: the same 16 games, the same kickoffs, the same totals and spreads,
the same absent FORM, the same `shootout` and `blowout_loss` base rates. The pasted pack cannot be
reconstructed by editing the committed one (the edited file hashes to `e47d061d…`), so its bytes
are not recoverable from inside this repository.

`runIngest` refuses a file whose `input_pack_sha256` differs from the sha of the `-pack` file on
disk (`beliefs_result.go:580`). Only one of the two shas can be written.

### Which of the two packs is right — resolved

The committed pack is the **stale** one. `beliefpack.py base_rates()` reads
`base_rate_held_out` from `app/internal/scenario/artifacts/belief.json`, which carries exactly the
pasted pack's numbers:

| scenario | in-sample (`base_rate`) | held-out (`base_rate_held_out`) |
|---|---|---|
| `efficient_offense` | 0.3243 | **0.3721** |
| `pass_heavy` | 0.3353 | **0.2648** |

So the pasted pack was generated by the current `beliefpack.py`; the committed
`week01.input.json`, dated 2026-08-24, predates the held-out fix. `beliefpack.py`'s own docstring
says why that matters: with the in-sample number in the pack, *"a forecaster saying nothing but
'0.37 everywhere' beat the in-sample reference by five points for free — ~30% of the target edge,
with no football knowledge."* Handing a forecaster the stale rate is not a neutral choice.

**The pasted pack cannot be reproduced in a fresh checkout**, whatever the base rates: the pack
embeds its own `generated_at` and the cache block's `fetched_at`/`sha256` for `games.csv`. A
re-fetch stamps today's time and would produce a *third* sha. The bytes behind `42bca9d8…` exist
only on the machine that ran `make belief-pack` on 2026-08-24 or later against that cache
snapshot.

## Decision

**Echo `42bca9d8…`** — the sha of the pack actually shown.

## Consequences

- The file does not ingest against the currently committed pack. That is a *visible* failure with a
  loud error message, which is the failure mode to prefer.
- Unblocking it means **committing the pack file that hashes to `42bca9d8…` from the machine that
  generated it**. Regenerating from a clean checkout will not do it — `make belief-pack` was
  attempted here and stops at `games.csv not found` (the ~500 MB nflverse cache is gitignored), and
  even with the cache the fresh `generated_at` and `fetched_at` guarantee a different sha.
- Where the two packs disagree — the two base rates — the **pasted** values are used, because they
  are the ones the forecaster was shown. This affects only abstained rows, where the contract says
  to write the base rate as a neutral placeholder: 11 rows in this file.

## Alternatives rejected

- **Echo `e4465d9e…`.** Ingests today. Rejected because the sha field exists precisely to prove
  which facts a forecast saw; writing a sha for a pack that was not shown defeats the one property
  ([ADR-002](./ADR-002-belief-log-tracked-in-git.md)) the whole probe rests on. It is also the
  worse pack on the merits, per the table above — it would bind the run to the stale in-sample base
  rates the tooling has already corrected.
- **Silently pick whichever ingests.** Rejected: it hides a real inconsistency in the pack pipeline,
  and the discrepancy in `pass_heavy` (0.2648 vs 0.3353) is large enough to matter to whoever
  reads the score later.

---

## Resolution, same day

The dilemma dissolved once the cache was available: `games.csv` was the *only* missing input, so
`make belief-pack SEASON=2026 WEEK=1` ran here and produced a pack that

- carries the **held-out** base rates (0.3721 / 0.2648) — the pasted pack's numbers, confirming the
  diagnosis above,
- carries the **current** market, which mattered more than expected: six of sixteen games had moved
  since 2026-08-24 (WAS@PHI total 47.5 → 44.5, NYJ@TEN spread 3.0 → 1.5, and four others), so the
  pasted pack was stale on price as well as on base rate,
- and is **committed**, so the forecast binds to a sha that exists in this repository.

The week-1 forecast now echoes `2392b66a…`, the regenerated pack, and ingests. Neither `42bca9d8…`
nor `e4465d9e…` is used. The decision recorded above — bind to the facts actually shown, never to
whichever file happens to be on disk — is unchanged and was what forced the regeneration rather
than a quiet substitution.
